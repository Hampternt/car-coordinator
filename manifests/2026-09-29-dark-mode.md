## Goal

On screen, Car Coordinator follows the computer's light or dark setting. A **Colours** switch lets you override that, for this browser only. It has three choices: **Follow the computer**, **Light** and **Dark**. It sits on the Data tab unless the owner picks the top bar (Owner questions).

- **The printed sheet** prints exactly as it does today, whatever the computer or the switch says: white paper, black text and pink marked rows. On the Print preview tab the sheet is the same white paper, and the page around it follows the theme.
- **Label colours** that people picked stay recognisable on a dark screen. The stored colour never changes.
- **Saved data:** nothing in the saved plan changes, and pressing the switch never saves the plan.
- **Later packs:** from this pack on, `docs/style.css` writes colours only as tokens, and a test enforces it. Packs 4 to 9 are therefore built on tokens from the start.

The pack ends with **Announce Dark mode and cut 0.5.0**.

## Saved data

**There is no migration: the saved plan's shape does not change.** These are all untouched: `carcoord:v1`, its schema version (v5 after pack 2), Backups, Archives, Export, the save file and share codes.

**One new per-browser key, `carcoord:pref:theme`:**
- It holds `light` or `dark`. Absent means Follow the computer, and any other value also reads as Follow.
- Only a press of the Colours switch writes it, through `Store.setPref`. Choosing Follow removes it (`setPref('theme', null)`).
- It is never written at boot. `theme.js` and `applyTheme()` only read, so pack 1's Design D startup order gains no step.
- It is not on `state`. It therefore never reaches Export, the save file, Backups, Archives (which hold `carcoord:v1` only) or share codes.

**Older builds** ignore the key and show the light app, so a downgrade needs no conversion. An older `style.css` ignores `data-theme`.

**Mixed cached files** (pack 1's Boot safety):
- **A stale `index.html` without `theme.js`:** `app.js` applies the theme at its top level. At most, the first paint is light for a moment, once.
- **A stale `store.js` without `Store.pref`:** a `typeof` guard reads Follow. A press still applies for the page and shows the "couldn't keep" line.
- **A new `app.js` with an old `style.css`:** the no-tag dots have no inline colour, so they fall back to the old CSS `#2e7d32`. Crew member chips lose their steel colour and show ink for one load. Both are cosmetic.
- **An old `app.js` with the new `style.css`:** the old inline `--c:#2e7d32` and `--c:var(--steel)` still resolve. `theme.js` still applies a stored choice.

**Upgrade check in the pack gate.** It runs from the 0.4.0 `dev` build, and again from the build live on `main` before `dev` → `main`. All of these must hold:
- `carcoord:v1` and every backup are byte-identical on open.
- One update archive holds the old `carcoord:v1` byte for byte.
- The note shows the 0.5.0 entry.
- `carcoord:pref:theme` is absent after the open.
- A reload shows no note.

### C. CSS structure (style.css)

1. `:root { light tokens; color-scheme: light }`
2. `@media screen and (prefers-color-scheme: dark) { :root:not([data-theme="light"]) { dark tokens; color-scheme: dark } }`
3. `@media screen { :root[data-theme="dark"] { the same dark tokens; color-scheme: dark } }`

Blocks 2 and 3 are the same list written twice, because plain CSS has no mixin. Smoke proves they agree token for token.

- **Form fields** use `--field`. `textarea.code` gets `color: var(--ink)`.
- **The sheet:** `.sheet` gets `color-scheme: light` and uses only paper tokens. In `@media print`, `body` uses `var(--paper)`.
- **Bright fills** (hi-vis, marker):
  - Text is `--on-bright`, including `.pick.on .pick-note` and `.pick.on.flag .pick-note`.
  - `.day.on.today { box-shadow: inset 0 -3px var(--steel-fill) }`.
  - `.tag-choice.on .dot, .pick.on .dot { --lift: 0%; --dot-edge: var(--edge-on-bright) }`.
  - The switch's pressed class gets `color: var(--on-bright)`.
- **`.notice.update`** is not a bright fill. It has a `--bar-bg` background, `--on-bar` text, and a `--hivis` edge and headings. Its ✕ keeps ordinary button colours: `.notice.update .btn { color: var(--ink) }`.
- **Pack 1's and pack 2's rules** move onto the same tokens:
  - the What's new and Archives cards (`.card`);
  - the static recovery line in `#notices`;
  - the archive and save-file buttons, where `.armed` is `--warn-fill` with `--on-fill`;
  - pack 2's print-tick column.

### D. Label colours

**Inside `@supports (color: color-mix(in srgb, red 50%, white))`:**
- `.chip { --c-shown: color-mix(in srgb, var(--c, var(--ink)), var(--ink) var(--lift)) }`
- `.dot { --c-shown: color-mix(in srgb, var(--c, var(--ok)), var(--ink) var(--lift)) }`
- The chip border and the dot fill use `--c-shown`. Outside `@supports` they use `var(--c, …)` as today, so an old browser shows the raw colour rather than an unset border.
- `.chip.on` keeps `background: var(--c)` with `--on-fill` text. Its border is `--c-shown`, so dark mode shows a lifted ring.
- The dot's border is `--dot-edge`, and on bright fills it is `--edge-on-bright`.

**Colours measured:** the fixture's five, plus #000000 and #000080. Black lifted 40% is #5d5d5c, which is only 2.43:1 on the panel. ### E. Applying the theme

**`docs/theme.js`**, loaded from `<head>` right after the stylesheet, as `theme.js?v=⟨APP_VERSION⟩`:

```js
try {
  const t = localStorage.getItem('carcoord:pref:theme');
  if (t === 'light' || t === 'dark') document.documentElement.dataset.theme = t;
} catch {}
```

**At the top level of `app.js`:**
- `applyTheme(v)` sets or removes `html[data-theme]`; only `light` and `dark` count. Called with no value, it reads `Store.pref('theme')` behind `typeof Store.pref === 'function'`.

- A `window.addEventListener('storage', …)` handles `e.key` equal to `'carcoord:pref:theme'` or `null`. It calls `applyTheme()` and then, once `start()` has run, `renderKeepingFocus()`. Neither writes.
