## Decisions and deviations

- Item 1, the 0.16.0 consequence: 0.16.0's `opUsable` checks only `schema <= SCHEMA` and `Array.isArray(changes)`, and `Sync.check` looks only at each change, so a top-level `at` is ignored and the op applied as before: no read-only, no mis-apply (tested against fce442f served from git). The other way round, a 0.16.0 peer's ops carry no `at`: `opTime()` reads it as null, and the review must show such a time as unknown. No schema bump.
- Item 1: `at` is the batch's, stamped when it is taken (`capture`). To make it the edit's time and not the reconnect's, `roomFlush` now takes the edits while not sending too (offline, or before the catchup is read) instead of returning first; the batch waits in the queue as before. Times of edits taken while not sending are also kept per edit (`r.times`, by `Sync.changeKey`) beside the base (`times` in carcoord:roomBase), so the first batch after a reload, which rebuilds them, takes their own times (its `at` the latest). Cleared once the queue is empty.
- Item 1: `drain()` now also returns the ops it applied (`{seq, oid, at, own, changes}`), and a flag carries its op's time as `opAt` only when the op had one (an exact-match round-2 check on flags stays as it was). `take()` gained a 4th parameter, the op's time.
- Fake relay: `cut(context)`/`mend(context)` take one browser offline while the others carry on.
- Item 2: `Sync.overlap(base, mine, theirs, from)` applies this browser's changes on top of the room's plan with `collision()`'s own rule, so its clashes are exactly the flags Send raises (property-tested against a replica's drain). A clash counts only where the room changed that field or item since the base: an edit whose `was` predates the base (a held box rebuilt after a reload) stays a live collision, flagged as it goes out, so round 2's held-box reload flow is not turned into a review. Field level, as the brief says: two different fields of one route merge cleanly, so they are not a clash (the owner's word was "lines"; recorded for the owner).
- Item 2: the room's ops given to overlap carry `own` (this browser's, sequenced before the drop): applied as part of the room's plan, never counted or timed as the other's.
- Items 3 and 6's Send landed as one commit (as round 2's items 2-4 did): with the hold alone, the round-2 offline section cannot pass, since one side stops and waits. The bar here is the bare three buttons; its words are item 4.
- Item 3, round-2 checks changed by design (every assertion kept, a step added): (1) "Offline and reload": the order is now fixed (B reconnects first via the fake relay's `cut`, A after it), it checks that A is held, and A presses Send my changes; its flags and convergence checks run unchanged after. (2) "An edit to a route the other removed and then reloaded over": b's offline edit is to a route removed meanwhile, so it is held; it checks that, presses Send, and the rest runs unchanged.
- Item 3, scaffold gap fixed: the four `room-review-*` actions were wired in `roomAction` but not listed in `ROOM_ACTS`, so a click never reached them. Added there (Shared plan code).
- Item 3, the hold: at a catchup, the queue's waiting batches (captured first) are a candidate; the catchup's ops are drained as usual, and `Sync.overlap` is run on the base before it, the waiting batches and the room's ops (own ones marked). Clashes raise `room.review` (state `held`); `roomFlush` then only captures (and keeps) and never sends, so edits made while held wait behind them. Live ops keep being applied, appended to the review and the overlap worked out again. Compaction and Push are off while held (a version is the screen, held edits and all; Push's button is disabled and roomPush refuses with a notice).
- Item 3, what the screen shows while held: the replica's shadow, the room's plan with the held queue on top, so `carcoord:v1` keeps the offline edits and they never live only in the hold record. Marks: `.room-offline` (dotted) and `.room-offline-clash` (solid), with a title giving both values and times.
- Item 3, persistence: `carcoord:roomBase` gains `review` ({id, state, baseSeq, base, from, oids, theirs, started, batches}), written by every base writer (roomBaseWrite's head includes it, roomHoldsKeep compares and rewrites it). On opening, the kept batches become the queue again (unsent) and the review is worked out again, so a reload neither forgets the hold nor rebuilds the edits on the moved base (which would send them unflagged). Kept as `sending` after Send until the room has confirmed every reviewed batch, then cleared. recover.html lists carcoord:roomBase as before; it holds plans and changes, never the secret.
- Known limit, for the concurrency review: two browsers back at the same moment can both read their catchups before either sends; neither sees the other's edits, neither is held, and the result is round 2's flagged merge (nothing lost silently). Only the second to read its catchup can see the first's edits.
- Item 4: "the other manager", as the brief says: `Presence` exposes no name in the contract. The pill note is its own element (`#syncReview`, styled as the flags count) beside the pill, so the pill's own text, which tests match exactly and pack 4 appends to, is untouched. The bar counts things (fields, items) as overlap lists them; M is how many of mine clash. A read-only room disables Send with one line; Keep still works.
- Item 5: Look first is an inline list on the card (`room.review.look`, kept on `room` so a redraw of the card keeps it open), not the round-1 dialog. Lines name things as the flags do (a car by its registration, a position by its name); a removal the other changed says which fields they changed; one the other removed says so.
- Item 6, Keep's Backup: the plan as it was on screen, which is the shared plan with the held edits on top (and any edits made while held), not the plan from before reconnecting. Restoring it later is the same as having pressed Send then, and it carries the other's non-clashing work too; the pure offline plan would undo theirs if restored. Named by the last offline change ("Kept from offline, 09:14"), or now when that time is unknown. Backups first, and nothing happens if it cannot be taken. A no-change op queued after a snapshot is not dropped.
- Item 7, "a review appearing on one tab only once": one review per browser, answered once. A tab opened (or reloaded) while held reads the kept hold and is held too, with the same review and batches; whichever tab answers says so under `carcoord:roomReviewAnswer` (set and removed at once; the room's id and the review's, never the secret) and every other held tab follows: Send there, this tab takes up the record of what was sent (marked sent, so nothing goes twice) and keeps it on screen until the room has it; Keep there, it drops the held edits and takes the shared plan (the Backup was taken there). A tab that stopped saving (round 2's planElsewhere) neither tells nor follows: what it holds is its own, and its plan is in Backups already. When two tabs are open as the connection goes, the offline edits saved in one stop the other (round 2), so the review appears only in the tab they were made in.
- Item 7, dropped while building: a live tab taking up a hold raised in another tab (on the base's storage event). It cannot happen: a tab following live saves every change it gets from the room, which stops the offline tab first, and a stopped tab never writes the hold. Removed rather than kept untested.
- Item 7, Leave while held: the held edits stay in the plan on this PC (they were on screen and in carcoord:v1), nothing is sent, the hold goes with the base. The armed Leave says so in one line beside Sure?; no dialog.

## For the concurrency + live-data review

- Record size: the kept review holds two plans (the base and, after compaction, the snapshot) and every op of the other's since the base, rewritten on each capture while held. A write refused for quota forgets the base (round 2's rule), and the hold with it: the edits stay in carcoord:v1, but the browser then reads as one with no record of the room (Not live, Take offered) rather than held.
- A tab that follows an answer given in another tab (Send there) marks the batches sent and relies on that tab's ops arriving to clear them; if it reconnects first it sends them again (same changes, harmless, no flag).
- Compaction past the base: this browser's own ops sequenced before the snapshot count as the other's in the snapshot's diff, which can raise a review that was not needed. Never a silent send.
- Replace-everything while held (Import, Restore from Backups, a share code, Restore a version): the confirm still says "This changes the shared plan for both of you", but the change is held behind the review like any edit; Keep drops it from the screen (it is in the Kept Backup).
- An older copy (0.16.0) opening a profile with a kept hold ignores `review`, rebuilds the edits from the moved base and sends them unflagged. Only on a downgrade.
- Two browsers back at the same moment: see the known limit above (round 2's flagged merge).
