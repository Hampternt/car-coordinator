## Decisions and deviations

- Fix 1, design: `Sync.overlap` keeps its per-field `clash` (what Send flags, still property-tested against a replica's drain, unchanged) and gains a line layer beside it: each change's `line` ({removed, theirs: [{field, value, at}], at}), `lines`, `lineLast`, `myLines`, `elsewhere`. A line is an item (kind+id) or a meta field; adds and orders are never a line. What the other changed on a line counts where it differs from this browser's end value, or where sending writes over it, so "both set the same value" is still no review. Property test added: every field clash is on a clashing line (300 random sessions, and >10 of them line-only).
- Fix 1, app: the review is raised on `lines`, the bar counts lines ("The other manager changed that line / one of those lines / N of those lines too (last …)"; "the rest is on your screen" uses `elsewhere`), the solid mark goes on every box of a clashing line (its title says what the other changed on the line), Look first is one row per line ("They changed its round to “5” (09:20)." for another field; "Theirs “…”" for the same field, as before). Send's hint now says both are kept and only a box both changed is listed with Put it back.
- Fix 1, round-3 test lines changed by design (owner's decision, not weakened): the bar's "changed one of them too" / "2 of them too" became "one of those lines too" / "2 of those lines too"; the time-unknown check nulls `lineLast` (what the bar now reads) instead of `clashLast`. sync.mjs's "different fields of one route: no clash" stays as it was: it is about `clashes`, which is still per field.
- Fix 2, choice: a held tab that hears another held tab's edit stops as round 2's stopped tab (planElsewhere, its plan in Backups, the pill says Reload this tab), rather than taking up the other tab's held batches. Taking them up cannot be made exact: the other tab's edit is in its plan before it is in a batch, two tabs' extra batches would need one agreed order (else they rewrite the stored review back and forth), and Follow's oid bookkeeping assumes one queue. The stop is quiet (the pill, no dialog) and loses nothing.
- Fix 2, what counts as another tab's edit (`heldTabEdited`): the stored review is this tab's own, still held, and the base beside the plan is at this tab's seq. A save that differs only by a change from the room (one tab has applied it, the other not yet) has the other seq, so it never stops a tab; the tab behind saves again once it has caught up and is judged then. A review answered there (gone, or being sent) does not stop it either: the answer follows.
- Fix 2, held edits are captured at once (`roomEdited` while held), not after the 300 ms gather, so a held tab writes its plan and the batch holding the edit in the same moment and another tab never reads one without the other. A side effect: while held, typing makes a batch per input event; they all wait behind the review and go out in order on Send (more ops, same result).
- Fix 2, a stopped held tab answers nothing: Send and Keep are disabled there with "Reload this tab to answer", and both refuse when called.
- Fix 2, follow-up (found while testing fix 3): the check read the base at the plan's storage event, but another tab's writes reach this tab one key at a time, in order, so at the plan's event the base beside it has not arrived yet. A tab one change from the room behind the other then read the old base (its own seq) and stopped for nothing; and Keep answered in the other tab stopped this one instead of letting it follow. Now a held tab judges the other's plan when the base written after it arrives (`heldTabCheck` on the carcoord:roomBase event), or 500 ms after the plan's event should none come. Reproduced at 0f042dd: sync-ui "neither tab stopped" (one held tab's frames delayed 1.5 s while the other applied a change from the room) got [true, false]. Fixed: check.sh OK; sync.mjs passed, 214 ok; sync-ui passed, 570 ok (2 new).
- Fix 3, choice: edits made while held are part of what Keep keeps (in its Backup) and are never sent, in the tab Keep is pressed in and in every tab that follows it (`roomKeepDrop`, shared by both). That matches the bar ("not sent until you choose", "with what you changed since") and the hint, which now ends "and nothing you changed since going offline is sent". A following tab puts its own screen into Backups first under the same label (free when it is the same plan: Store.snapshot skips one identical to the newest), and stays held if that cannot be taken.
- Fix 3, Send followed in another tab: the follower takes up the answering tab's whole stored queue as sent (held batches and those made while held alike), not only the reviewed oids, so an edit made after the hold and read by a tab opened later is not sent twice. An edit only the follower holds is its own and still goes out (none in practice: a held tab stops when another one edits, fix 2).
